# App-owned HTTP and explicit data/error boundaries

The next-stage refactor chooses application-owned HTTP execution rather than a reusable server library, and separates business failures from their HTTP representations. Every workspace now uses `@app/*`; `@app/server` is the existing app, not a library. This trades some explicit translation and renaming for clear dependency direction and one discoverable application composition root, without changing domain terms, wire contracts or stored data.

## Supersession and ownership

This supersedes ADR 0011's server-library placement, server-app name, shared operation-error ownership and nested index/model entrypoints, and conflicting earlier placement/naming choices. Its default capability layers, private persistence boundaries, exact joined-read exceptions and real-persistence testing remain. ADR 0010's isolate/invocation lifetime remains authoritative; prior ADRs retain their historical rationale. Variant remains the domain term; ProductVariant is the shared TypeScript namespace, not a new entity.

- Shared schema owns data and reusable commands only: flat singular modules expose `Product.Info`, `ProductVariant.Create`, and equivalent model namespaces, retaining fields, brands, encodings and distinct operation-input schemas.
- Core owns business errors and public named capability files beside private implementation directories, with no `index.ts`. `Service`, `Interface`, stable `layerNoDeps` and default `layer` remain. Products and ProductVariants share persistence; external features use their public capabilities. Each feature's `errors.ts` defines its public business errors once and self-exports a capability-named namespace (`ProductsErrors`, `ProductVariantsErrors`, etc.). The public capability explicitly re-exports that namespace, not individual constructors; there are no package error subpaths. Internal consumers import the owning error module directly, so ProductVariants can use ProductsErrors without loading the Products implementation. External consumers import the namespace through the public capability. Error modules depend only on Effect and shared data types; private repository conflicts and operational port/provider errors stay with their existing owners. Importing a business error does not require its owner's Service.
- Protocol owns independent serializable errors, status annotations, flat resource groups and wire projections. It imports schema and Effect, never core or db. Identical tags/fields on core and protocol errors are intentional wire compatibility, not a reason for a shared error framework.
- App handlers explicitly construct protocol errors. Operational SQL/storage/execution failures retain safe operation-only diagnostics and the existing empty 500 response, without leaking causes, converting failures to defects, retrying writes or publishing new errors. `NoExtractedData` remains protocol-only because core returns Option.
- Database table exports use `Table` suffixes. Products and ProductVariants share `db/schema/products`; Listings and ListingVariants share `db/schema/listings`, with no nested variant schema subpaths. Colocation follows persistence ownership rather than one-file-per-table. Physical tables, constraints, registry relations and append-only migrations remain unchanged; boundary tests enumerate individual table symbols (including imported aliases), not module-wide permissions. Better Auth's model keys and the importer's persisted keys do not follow TypeScript symbol renames.

Effect service, middleware and context-reference keys use the current workspace and module identity, such as `@app/core/retailers` or `@app/core/products/repository`. Root services use the package name (`@app/db`, `@app/client`); named references and multiple tags in one module append the symbol (`@app/core/scrapes/trace/RootTraceId`, `@app/protocol/auth/security/CurrentUser`). Test keys include the workspace and test module path. These globally unique dependency-injection keys are not import/export declarations: a private repository key does not expose a package subpath. They do not rename error tags, HTTP identifiers, persisted values or resource identities. Boundary tests check module ownership and collisions across production and tests.

Production workspace directions are schema→Effect, db→schema, core→db/schema, protocol→schema, client→protocol/schema, infra→core/db/schema, server app→core/db/infra/protocol/schema, web→client/schema. Db has no core dependency even in tests. Apps expose no invented library barrel, and no background app is added: HTTP, auth, cron and both Workflows remain one Worker.

## Module resolution

Relative TypeScript imports and re-exports omit `.ts`/`.tsx`, including namespace self-exports. TypeScript uses `module: preserve` and `moduleResolution: bundler`, matching Bun, Vite and Alchemy's installed Oxc loader. Package export targets, tsconfig file paths, tool entrypoints and file URLs still name actual files with extensions; no extensionless package-export targets or private compatibility exports are added.

Bare Node's ESM resolver is no longer a supported way to execute this source graph. Node init-order regressions install Alchemy's existing `nodeLoaderArgs` hook, exactly as its CLI does, and still run native Node module evaluation rather than Vite's module runner. The standalone importer runs with Bun. Emitted workspace output is not a standalone bare-Node distribution; public package exports remain explicit source paths. Runtime/lifetime rules and the dynamic Playwright import boundary remain unchanged.

## Composition and lifetime

`apps/server/src/Worker.ts` directly default-exports `Cloudflare.Worker("Server", ...)` and owns FeaturesLayer/ApplicationLayer/DatabaseLayer/InfraLayer/HttpLayer. `http.ts` assembles the nine directly named handler Layers, auth/discovery mounts, docs and health; there is no server composition module or forwarding factory. Named app/test Layer values use PascalCase with a Layer suffix, while core's public `layer` and `layerNoDeps` remain lowercase.

Resource properties resolve Stage/AlchemyContext/Config through installed Alchemy Effect-valued inputs. The root provides the actual Postgres and Bucket handles through their typed resource Self services; Worker prefers those during planning and falls back to typed refs for standalone/runtime evaluation. Alchemy's refs read persisted state, so using only refs would break a fresh stage and miss current-plan replacement dependencies. Root logical ids, resource options, guards, bindings and deployment behavior are preserved.

The runtime builds one application context and reuses it for both HTTP and cron; reusing only a Layer value across independent builds would create two adapters. No database I/O occurs during planning or graph construction. The adapter resolves the connection in the invocation scope; Better Auth stays lazy and runs foreign adapter calls through its request-state invocation bridge. Telemetry is registered with Alchemy and flushes via its event scope/waitUntil. Workflow steps build and close independent contexts. Configuration remains typed in layers; at Worker initialization only it aborts the isolate under Alchemy's `E = never` contract.

## Evidence and guardrails

Resolved-import tests cover workspace exports, relative imports, re-exports, dynamic literal imports and TypeScript aliases. Core tests enumerate exact repository consumers, joined-read tables and write sets; ADR 0011's read-owner/Cascade exceptions are retained, not broadened into directory permissions. The importer and health `select 1` remain specific infrastructure/entrypoint exceptions.

Offline Worker tests execute the actual default resource with installed Alchemy services and resolve its properties/bindings against both empty and stale state. They complement, rather than replace, real-persistence HTTP/cron sharing and independent Workflow-step scope tests. HTTP tests distinguish core/protocol class identities and check exact failure fields, status/body and operational redaction. Schema parity, original OpenAPI and migration hashes, no-op generation, real PostgreSQL races and browser/auth tests protect behavior.

E12's fake-repository exemplar is deliberately replaced by `layerNoDeps` over real repositories/Db: a nontransactional sequence/trigger with a positive control proves no insert is attempted for a missing Product. A skipped PostgreSQL race is never evidence. A declaration build that exits nonzero on Effect warnings/suggestions remains nonpassing; no diagnostics are suppressed to call it green. Offline planning does not replace separately authorized deployed binding smokes.
