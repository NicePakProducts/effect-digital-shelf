# Repositories are services provided by their feature

A repository (`<Area>/repositories/<Entity>Repo.ts`) is a `Context.Service` class named `<Entity>Repo` whose `make` captures `Db` once and keeps the query surface it had as a module of functions: one query per method, results decoded through `Sql/Rows.ts`, the existing error vocabulary (including the existing uniqueness errors), never opening a transaction. Its layer is one `static readonly` field, `static readonly layer = Layer.effect(this, this.make)`. A feature (`<Area>/<Feature>.ts`) yields the repos it calls in its own `make`, binds each to a named variable, and provides them itself: `static readonly layer = Layer.effect(this, this.make).pipe(Layer.provide([BrandsRepo.layer, CascadeRepo.layer]))`. `Layers.ts` therefore composes features only; it no longer knows which repositories exist, and `Brands.layer` is `Layer<Brands, never, Db | Cascade>`.

ADR 0003 rejected service repositories because "nothing varies across that seam", and that is still true: repositories are never faked, and tests still run the real queries on PGlite. What changed is the reason for the seam. It is not there so a test can swap the implementation. It is there so that a feature declares and provides its own persistence (the shape of slopcop's `LabelingRules`, `.repos/slopcop/packages/labeling/src/LabelingRules.ts:705`), and so that dependency capture moves into the repository's construction. Today a function repository's `Db` requirement leaks into the `R` of every feature method that calls it, and each feature closes it again with a `withDb` wrapper on every method; a repository service holds `Db` itself, so the wrappers go and the feature's layer says which persistence it uses. The seam is paid for once per feature, not per call site.

## The invariants the seam depends on

- **One `Db` per invocation.** `withTransaction` keeps the reserved connection in the running effect's services under a key minted per `SqlClient` instance (`.repos/effect/packages/effect/src/unstable/sql/SqlClient.ts:142`, `TransactionConnection(clientIdCounter++)`), and each query resolves that key at run time. A repository that captured `Db` at construction therefore joins any transaction the calling feature opens, as long as its `Db` wraps the same client. A separately constructed SQL client carries a distinct key, so a repository whose `Db` wraps a second client inside one request or Workflow step runs outside the caller's transaction with no type error, even though both values satisfy `Db`. So `Layers.ts` leaves `Db` unresolved, infra provides it exactly once per invocation (ADR 0006), and nothing in core builds a `Db` of its own.
- **Stable layer references.** Effect memoizes a layer by object identity inside one build (`Layer.ts:421-450`), and `Layer.provide` threads the same memo map into the dependency build (`Layer.ts:1339`), so six features providing `CascadeRepo.layer` construct it once. That only holds while every reference is the same object: `.layer` is a `static readonly` field on every repository and feature, and a layer allocated on access (a getter or function that builds a new one) defeats sharing because each allocation is its own memo key. Memoization follows the live memo map, which a build may inherit from its parent; `Layer.fresh` starts an independent map, and separate invocations must not share or inherit cached services.
- **Closed method environments.** `Layer.provide` discharges a layer's construction requirements, not the `R` of the effects its methods return, nor the requirements of a module-level helper the method calls. A public method type never carries a `*Repo` in `R`. A helper shared across features (`Scraping/Transitions.ts`, whose `transition` and `transitionExtraction` call `ScrapesRepo` and `ExtractionsRepo` at module level and are imported by `ScrapeRunner`, `Extractions`, `ExtractionRunner`, `Scrapes` and `Scheduling/Sweeps`) either takes the repo service as a parameter or has its returned effect wrapped in `Effect.provideService` with the repository instance the feature captured in `make`. Providing the construction layer is not the same as binding the returned effect; method `R` is checked separately from layer `R`.

## Rules

- **Private persistence, public peer.** A feature provides the repositories it directly uses and does not export their tags; several features may provide the same repository layer, which is one memoized instance per build. A sibling feature that is itself a public service with its own tests and callers (`Catalog/Cascade`, which owns the collect-then-delete transaction and the R2 cleanup) stays in the feature's construction `R` and is provided once in `Layers.ts` with `provideMerge`, as today. The literal slopcop shape, which provides `GitHubClient.layer` inside `LabelingRules.layer`, is not copied for peers: a peer provided inside several features stops being visible as a dependency of the entrypoint, even though its own layer stays independently buildable.
- **One `layer` by default; `layerNoDeps` only where a second assembly exists.** slopcop keeps the pair because its tests build `layerNoDeps` over substituted dependencies. Repositories here are never substituted, so a feature whose only internal dependencies are its repositories exposes `layer` alone. A feature or adapter exposes `static readonly layerNoDeps = Layer.effect(this, this.make)` beside `layer` only when an existing alternate assembly changes a dependency that `layer` supplies internally (a test replacing a peer service that `layer` provides, or `Layers.ts` composing such a peer differently). Supplying a peer that `layer` already leaves unresolved does not qualify, an alternate assembly still supplies the real repository layers, and an adapter with no internal `Layer.provide` has nothing to split.
- **Error vocabulary preserved.** Repository failures stay what they are today: `SqlError` with its `reason` (unwrapped at `Sql/Errors.ts`), the entity's not-found error, and the repo-local uniqueness errors that already exist (`DomainTaken` in `RetailersRepo`, `PageTaken` in `PagesRepo`, and the domain's `DuplicateVariantName` raised from `VariantsRepo`). No new generic per-repository wrapper classes are introduced; a feature keeps matching on `reason` or on the existing tagged errors.
- **Named inputs on feature seams only.** A feature's public method takes one named input object when the operation carries data and more than one argument (`brands.update({ brandId, command })`); a parameterless `list` and a method that takes exactly one existing command struct are left alone. Input schemas live in `packages/domain` beside the commands. Repositories stay positional (`repo.get(id)`).
- **`orDie` policy.** Configuration and provider setup failures stay in the layer's `E` (`Config` errors, a malformed retry policy, a missing provider key), so they surface where the layer is built: at the entrypoint composition in `apps/server`, per invocation, before the handler, cron body or step body that depends on the layer runs, and each entrypoint handles that construction failure. Operational provider failures (a fetch that fails at request time) stay in the method's `E`, as they are today. Two sites stay defects, each marked with a `SAFETY:` comment stating why a failure can only be a bug: row decoding in `Sql/Rows.ts` (the table is the entity's definition, ADR 0002) and the decoding of Workflow parameters that this codebase encoded in `apps/server`. The blanket `orDie` on a Workflow task body (`WorkflowSupport.ts`) also receives operational failures today and is classified separately in the server area PR. A `SAFETY:` comment documents a defect; it does not handle one, so a site that a caller could reasonably recover from is not eligible. The site-by-site inventory (auth request failures, generated-id decoding, extraction projection decoding, metadata encoding) is settled inside the area PR that touches each file.
- **Repositories are never faked.** Tests build a feature over the real `Db` (PGlite by default, Postgres only where two transactions must overlap, unchanged). `core/test/Boundaries.test.ts`, which today scans only `src/`, gains a rule with the proving PR that nothing under `test/` provides a `*Repo` tag except through its real `.layer`. The rule is a syntactic scan: it rejects `Layer.succeed(XRepo, ...)`, `Layer.effect(XRepo, ...)`, `Context.make(XRepo, ...)` and `Effect.provideService(XRepo, ...)` under `test/`, and allows `XRepo.layer` and `XRepo.layer.pipe(...)`. It does not see through aliases, re-exports or helper-produced layers, so a green run is a guard against the obvious shape, not a proof of provenance; review carries the rest.

## Considered options

- **Function repositories, as ADR 0003 had them.** Rejected: every feature method re-provides `Db` through a wrapper, the requirement leaks into helper signatures, and the feature's layer says nothing about which persistence it uses.
- **Per-repository error classes wrapping `SqlError`, as slopcop does.** Rejected: the features already match on `SqlError.reason` and on the three existing tagged errors, and a wrapper per repository would restate that vocabulary without adding a case.
- **Features providing `Cascade.layer` internally, the literal slopcop shape.** Rejected as above: `Cascade` is a peer, not private persistence.
- **`layerNoDeps` on every service unconditionally.** Rejected: with repositories never substituted, the second layer is dead weight on most features and invites a test to assemble a feature over something other than its real repositories.

## Consequences

- ADR 0003's rule set for the methods inside a repository stands: one query each, decoded through `Sql/Rows.ts`, no transactions, imports limited to domain, Drizzle, Effect and `Sql/`. Only the module's shape changes, from exported functions to a service class.
- A feature's `make` reads its repositories once and binds each to a named variable; the `withDb` wrapper on every method goes away, because the repository already holds `Db`.
- `Layers.ts` composes features and peers only. Adding a repository to a feature changes that feature's `layer` and nothing else.
- The proving PR (`Catalog/Brands` and `Catalog/Cascade` end to end) must demonstrate: a repository constructed before the transaction opens still joins it, a rollback after a real write leaves no row, one instance per repository within one memo map, isolation across independent builds over distinct bindings, and repository-free method types on `Brands` and `Cascade`. Shared helpers (`Transitions.ts`), provider failure classification, alternate assemblies and the other areas' error preservation are proved by their own area PRs.
- `AGENTS.md` records the code style principles that accompany this shape, and `vite.config.ts` enables `prefer-const`, `no-else-return` and `no-lonely-if` at `error`; the tree has no violations of the three today, so no warn step is needed.
