# Shared dependency-bearing logic is a service its consumers provide

_Placement and wiring superseded by [ADR 0011](0011-explicit-packages-and-feature-owned-persistence.md); the historical decision below is retained._

`Scraping/Transitions.ts` holds the lifecycle rule of ADR 0004: a conditional update on the expected source status, a re-read when nothing changed, and a classification of the miss as `already_applied` or `rejected`. Five features run it (`Scrapes`, `Extractions`, `ScrapeRunner`, `ExtractionRunner` and `Scheduling/Sweeps`, eleven call sites), and it calls the Scrapes and Extractions repositories. Today those repositories are modules of functions whose effects require `Db`, which each consumer binds with a `withDb` wrapper; once ADR 0008 turns them into services, the helper acquires repository-service requirements of its own, and ADR 0008's closed-environment invariant says those must be discharged before a public feature method returns its effect. The decision (retro of the proving slice, 2026-09-11): the effectful part of the rule becomes a `Context.Service` named `Transitions`, with methods `scrape` and `extraction`, a `make` that yields `ScrapesRepo` and `ExtractionsRepo`, and one `static readonly layer` that provides both. Each consumer will yield `Transitions` in its `make` and provide `Transitions.layer` beside the repository layers it directly uses; `Layers.ts` continues to omit it, as it omits repositories. The transition table, the three pure helpers (`isTerminal`, `canTransition`, `classifyMissedTransition`) and `TransitionRejected` remain module exports: a pure function takes no service, the server's step helper matches the error by its tag, and the Workflow tests import the class. The same shape applies to a future helper that several features share and that itself needs a repository or a client, when that helper is private implementation of its consumers. Sharing and dependency capture alone do not make a service private: a public peer with its own tests and callers (`Catalog/Cascade`) keeps ADR 0008's entrypoint composition.

## Where each piece of the decision comes from

- **Not a parameter.** The `effect-program-design` skill (humanlayer/ampere, `.agents/skills/effect-program-design`, `main` as fetched on 2026-09-11) says so twice: creed 2 in `SKILL.md`, "Do not pass services, layers, effects, or errors as ordinary values when composition expresses the relationship", and `references/SERVICES_LAYERS.md`, "Yield dependencies from the environment rather than accepting service instances as parameters". `references/DEEP_MODULES.md` adds "Keep dependencies ambient in the Effect `R` channel."
- **A service with a layer that provides its dependencies.** The skill supports ambient dependencies and prefers services for capabilities, but does not require this helper to become one, and its assembly guidance (`SERVICES_LAYERS.md`, "Runtime composition owns assembly") differs from the private-layer convention ADR 0008 adopted; the choice is local, extending ADR 0008. slopcop supplies examples of the shape: `LabelingRules.layer` provides five repositories and `GitHubClient` (`.repos/slopcop/packages/labeling/src/LabelingRules.ts:112`, `:706-715`), `PolicyFacts.layer` provides `GitHubClient` (`PolicyFacts.ts:110`, `:254-256`), `GitHubClient.layer` provides its auth and HTTP dependencies (`.repos/slopcop/packages/github/src/GitHubClient.ts:991-996`). slopcop also uses other shapes: `evaluateAiLabelingRule` accepts a service value inside its named input (`AiLabelingRuleEvaluator.ts:34-50`), and `makeLabelingRuleCommands` captures repositories without a service tag (below). Its production source has one literal `Effect.provideService`, binding a request-derived identity (`apps/api/src/Labeling/httpapi/Security.ts:21`), none around a shared helper.
- **Provided privately by each consumer.** ADR 0008 makes directly used repositories private construction dependencies of a feature. Repeated references to a stable repository layer share one construction through the same live memo map (`.repos/effect/packages/effect/src/Layer.ts:432-455`; dependencies receive the same map at `:1339-1346`); `Transitions.layer` and its consumers will reference the same `static readonly` repository layers, so a build constructs each repository once within that map. Invocation isolation is ADR 0008's separate requirement that builds neither reuse nor inherit services captured over another invocation's `Db`.

## Considered options

- **The repository's service value as the first parameter**, `transition(repo, id, from, to, patch)`. Explicit in the signature. Rejected under the adopted convention against ordinary service parameters; it is also the shape of the `withDb` threading this map removes, though the two are different forms of explicit wiring and their maintenance cost is a judgment, not a measurement.
- **A module-level `Effect.fn` with the repository in `R`**, the consumer binding it with `Effect.provideService(ScrapesRepo, repo)` at each of the eleven calls or once in its `make`. This is the skill's own example (`references/SERVICES_LAYERS.md`, `listWidgets(input).pipe(Effect.provideService(WidgetProvider, provider))`) and what ADR 0008's invariant first offered. Rejected: we prefer a named private dependency; slopcop's lack of this wrapping for shared logic is precedent, not a correctness advantage.
- **A sub-`make`**, `makeScrapeTransitions = Effect.gen(function* () { const repo = yield* ScrapesRepo; … })`, yielded during each feature's construction so the repository layers the feature already provides satisfy it: slopcop's `makeLabelingRuleCommands` (`.repos/slopcop/packages/labeling/src/LabelingRuleCommands.ts:172-175`, consumed at `LabelingRules.ts:204` and satisfied by `:707-714`). No helper tag, no helper layer; each feature gets its own closure over the repository services, and repository memoization and captured-`Db` lifetime matter exactly as they do for the service. The Codex evidence review of this ADR preferred it: the rule has no state, no resource and no lifetime of its own, so a tag buys nothing the runtime needs, and the `Effect.fn` span names already identify the operations in traces. Chosen against because the service form gives the ADR 0004 rule one name and one place in the graph: the five consumers declare it in the same `Layer.provide` array as their repositories, and a reader or an agent finds who applies the rule by searching one tag. Reconsider the sub-`make` if that navigation and assembly boundary turns out unused, or if maintaining `Transitions.layer` adds wiring the consumers do not otherwise need.

## Consequences

- `Transitions.layer` provides `ScrapesRepo.layer` and `ExtractionsRepo.layer`; a consumer such as `Scrapes` provides `ScrapesRepo.layer` and `Transitions.layer` together, one construction of each repository within the build's memo map.
- `Scheduling/Sweeps` provides a Scraping-internal service. Today it imports the Scraping repository functions directly, and core's Boundaries test permits that inter-area implementation dependency; nothing here changes the boundary rule.
- ADR 0008's closed-environment sentence, which offered "parameter or `provideService`", is amended to point here; so is the AGENTS.md convention that repeated it.
- `core/test/Scraping/Transitions.test.ts`, which today calls the helper directly over `CoreTest.layerTest`, migrates to the real `Transitions.layer` over the test `Db`, keeping its apply, replay and rejection assertions; `Cascade.test.ts` shows the form for supplying a real repository layer. The Boundaries test-seam scan would not reject a substituted `Transitions`, since its rule matches only `*Repo` names; review carries that.
